口径：延迟为客户端发起至完整接收响应的耗时；P95 使用 nearest-rank（排序后第 `ceil(N*0.95)` 个）。成功要求 HTTP 200 且业务 `code=0`，健康接口还要求 `data.status=UP`；其余全部计为错误。公告所有 48,899 个错误都是 HTTP 429，没有网络错误或 HTTP 5xx。不能把 429 的快速返回当成业务处理能力，也不能仅凭全响应 P95 判断正常业务延迟。

逐请求原始采样在三个 `*.ndjson.gz` 中，每行包含请求起始偏移、延迟、HTTP 状态及业务成功标记。`load-summary.json` 保存环境、固定条件和完整精度的汇总，三个独立 JSON 保存各组结果。压测结束后健康检查仍为 HTTP 200 / `UP`，见 `postcheck.json`。

### 一个已证实的吞吐限制：单 IP 滑动窗口限流

`IpRateLimitFilter` 对普通 API 使用每 IP **300 次/分钟** 的 Redis 滑动窗口，`/api/health` 被豁免。公告请求在进入 Controller 前依次执行 `ZREMRANGEBYSCORE`、`ZADD`、`EXPIRE`、`ZCARD`，超过阈值直接返回 429；超过阈值的请求也会进入窗口。

因此单 IP 连续业务请求的长期允许速率约为 **5 req/s**。本次 20 秒测量包含空窗口的初始突发，成功 296 次（14.80 req/s）不能外推为每秒可持续处理 14.80 次。高并发下这些 Redis 操作并非原子整体；后面的请求可能在前面的请求计数前入窗，因此成功数也不保证恰好等于 300。这是从实现推导的并发边界，不另称为实测定位出的数据库故障。

增加并发不能绕过这一业务门槛。若下一步要测数据库容量，应另建隔离测试配置或受控多客户端场景，在保留限流策略的前提下单独定义业务负载和数据规模，并采集数据库/连接池指标。当前结果没有证明 MySQL、Redis 或 AI 模型达到容量上限；健康接口也没有数据库和模型工作量。

## 3. Agent 故障注入、失败记录与修复

测试真实 `ChatAgentLoop` 状态图及内存检查点，mock 的只有外部模型流和工具注册表执行边界。不依赖真实 AI、网络或用户数据。Flash/Pro 共用测试契约，没有引入第二套循环或自动模型切换。

| 场景 | 修复前实测 | 修改 | 修复后实测 |
| --- | --- | --- | --- |
| 超时：模型不再产生有效事件 | Flash/Pro 均超过测试外层 2 秒保护，未自行终止（2 失败） | 模型事件流增加空闲超时，默认 90 秒；超时取消上游并向现有失败处理路径传播，不重试 | 注入 80 ms 空闲超时后，两种模型均抛出根因 `TimeoutException`，上游取消，模型只调用一次 |
| 工具报错 | 已能回填合法 tool 错误消息并继续模型下一轮（2 通过） | 保留原有恢复行为；错误结果也纳入本轮重复调用回执 | 解析错误 JSON、核对 tool_call_id、验证继续回复及仅执行一次，全部通过 |
| 重复调用：相同 run 内同一 tool_call_id 跨轮再次出现 | 两种模型都执行两次，违反预期（2 失败） | 工具结果随图状态进入检查点；重放复用结果，同批重复折叠，同 ID 内容冲突拒绝 | 两种模型均只执行一次、只累计一次工具成功计数，后续仍有合法 tool 结果并完成回复 |

初始新增 6 项：**4 失败 / 2 通过**，见 `before-fix.txt` 与 `before-fix.xml`。超时测试先加可注入时间字段作为测试接缝，再在缺少 `.timeout()` 的原执行路径上运行；失败来自真正的 2 秒挂起，不是编译错误或缺失字段。

修复后扩展为 **16 项全部通过**，见 `after-fix.xml` / `after-fix.txt`；其中包含原先 6 项，以及同批重复、失败回执重放、同 ID 参数冲突、不同 ID/不同 run 不误去重、审批暂停后重建循环并恢复等边界。

原审批回归 `aSecondApprovalInTheSameTurnAsksAgain` 的夹具原本反复使用同一个 ID，和新增重放语义冲突。首次联合回归因此出现 1 项失败。已把第二个真实新写入改为独立 ID 和内容，仍然要求再次暂停并等待批准，没有删除或放宽审批断言；最终原有审批测试全部通过。

### 运行语义与边界

- `AI_STREAM_IDLE_TIMEOUT`（配置 `moodcopilot.ai.stream-idle-timeout`）默认 `90s`，是**相邻有效模型事件的空闲上限**，不含等待人工审批的时间；不是整轮聊天的总时长，也不是同步工具的执行期限。底层 WebClient 原先已有网络超时，本次为 Agent 层补独立的事件空闲保护，不能据 mock 的挂起声称原 HTTP 客户端完全没有超时。
- 去重键只在当前 run 内使用 **tool_call_id**，不是按参数语义合并。不同 ID 的合法重复查询/写入仍按原权限和审批执行；不同 run 不共享回执。同 ID 但工具名称或参数文本不同会失败关闭。
- 成功、失败、拒绝回执都保存，重放不会再次产生写入、引用事件或审批弹框。新的写入 ID 仍需独立审批。
- 这是检查点层的重放保护，不是数据库级 exactly-once：进程若在工具提交之后、检查点保存之前崩溃，仍可能存在副作用已完成但回执未保存的窗口。并发重复启动同一 run、跨进程崩溃后的业务幂等，需要另行在具体写入工具/事务层实现，不能由本测试证明。
- 此次未启动或重启用户后端加载修复，也没有部署；修复结果由源码回归和重新打包验证。
